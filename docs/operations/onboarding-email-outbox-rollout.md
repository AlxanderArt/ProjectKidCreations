# PKC onboarding email outbox — ordered Preview rollout and rollback

This procedure is an approval-gated release plan. It does not authorize a database mutation, credential change, n8n import, workflow activation, deployment, or email canary.

## Immutable scope

- Preview only.
- Production, canonical DNS, predecessor workflows, and customer records remain unchanged.
- Intake candidate path: `pkc-onboarding-durable-email-v3`.
- Sender OAuth principal must read back exactly `projectkidcreations@gmail.com`.
- Gmail API acceptance is not inbox delivery.
- No step may describe an email as sent or delivered based only on PostgreSQL, Sheets, queueing, or Gmail API acceptance.
- Ambiguous transmissions are reconciliation-only and must never be reset to pending or blindly resent.

## Required artifacts

1. Migration `db/migrations/003_onboarding_email_outbox.sql` and its exact manifest checksum.
2. Inactive Phase One package generated by `scripts/n8n-phase-one-candidate.mjs`.
3. Inactive dispatcher/reconciler package generated by `writeOnboardingEmailOutboxPackage()`.
4. Exact pinned n8n runtime identity from both package manifests.
5. A reviewed cutover commit that changes the proxy/UI only after all workflow activation readbacks pass.

Recompute hashes immediately before each gated action. If bytes differ from the reviewed candidate, stop and renew tests and review.

## Ordered release gates

### Gate 0 — additive onboarding role provisioning

This gate requires separate database/credential authorization and runs before migration `003`. Do not reapply the broader `db/roles/000_roles.sql` to an existing predecessor environment.

1. Read back whether `pkc_onboarding_runtime` and `pkc_onboarding_email_worker` exist, their exact attributes, memberships in both directions, database `CONNECT`, global role settings, and database-specific role-setting rows.
2. If either role is absent or drifted, open only the approved administrative role-provisioning window and execute `db/roles/004_onboarding_roles.sql` with `expected_database` bound to the exact target database. The script is additive, target-guarded, does not mention `pkc_mfa_migrator` or `pkc_mfa_owner`, and clears target-database setting overrides.
3. Establish or rotate each LOGIN credential through the protected secret mechanism. Do not place passwords in SQL files, command-line arguments, logs, n8n exports, or chat.
4. Read back exact hardened attributes (`LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOINHERIT`), no memberships, target-database `CONNECT`, global `statement_timeout=5s`, `lock_timeout=2s`, and `idle_in_transaction_session_timeout=10s`, and zero target-database role-setting overrides.
5. Open one real LOGIN connection as each role without printing credentials; require the expected database identity and require direct table access and unrelated MFA-function access to remain denied.
6. Confirm the migrator remains sealed before proceeding. Stop on any unexpected membership, privilege, setting, login, or target mismatch.

### Gate 1 — exact migration authorization

1. Snapshot the current database authority and migration ledger through the approved protected process.
2. Confirm migrations `001` and `002` match their recorded checksums byte-for-byte.
3. Apply only migration `003` through the bounded migrator window after separate approval.
4. Seal the migrator again.
5. Read back the exact ledger row, tables, constraints, functions, ACLs, role graph, role-level timeouts, and zero unexpected ownership through `db/readiness.mjs`.
6. Stop on any checksum, catalog, ACL, role-setting, or readiness mismatch.

### Gate 2 — inactive workflow imports

While Preview still routes to `pkc-onboarding-consent-v1`:

1. Import the exact Phase One, dispatcher, and reconciler workflow bytes as inactive workflows.
2. Keep MCP disabled and execution retention disabled.
3. Bind only credential references approved for each workflow; never embed credential IDs or secret values in repository artifacts.
4. Export/read back all three workflows.
5. Verify exact topology, inactive state, webhook/schedule state, credential names, retention settings, retry suppression, and package hashes against the reviewed artifacts.
6. Confirm the new webhook path has no active owner and the predecessor path still has exactly one active owner.

### Gate 3 — native runtime and OAuth proof

No email may be sent during this gate.

1. Use the exact digest-pinned n8n `2.19.5` runtime in an isolated disposable rehearsal.
2. Prove PostgreSQL parameter replacement, Code/IF/error-output behavior, one-item claims, bigint-string fences, exact raw JSON bytes, zero implicit HTTP retry, interruption cleanup, and import/export readback.
3. Prove Gmail reconciliation requests include both `labelIds=SENT` and `in:sent rfc822msgid:<...>`, request `maxResults=2`, and accept only one result with no `nextPageToken`.
4. Through the bound OAuth credential, call the non-sending Gmail profile/readback endpoint and require the authenticated mailbox identity to equal `projectkidcreations@gmail.com` exactly.
5. Confirm the credential scopes are no broader than the reviewed send plus reconciliation/profile requirements.
6. Stop if the runtime changes request bytes, retries, broadens search, exposes PII, or cannot prove the OAuth principal.

### Gate 4 — worker activation

After separate approval:

1. Activate the reconciler and read back its active state and exact bytes.
2. Activate the dispatcher and read back its active state and exact bytes.
3. Verify there are no pending, transmitting, ambiguous, or accepted onboarding rows before intake activation.
4. Do not manually execute either worker and do not create a synthetic outbox row.

### Gate 5 — isolated intake activation

After separate approval:

1. Activate the Phase One v3 intake on `pkc-onboarding-durable-email-v3`.
2. Read back its active state, exact bytes, credential binding, retention, and webhook ownership.
3. Confirm the predecessor `pkc-onboarding-consent-v1` remains active and Preview still routes to it.
4. Do not submit a signup or email canary.

### Gate 6 — separate Preview cutover

After Gates 1–5 pass:

1. Create a separate UI/proxy cutover commit; do not mix migration or workflow-source edits into it.
2. Require the proxy to target `/webhook/pkc-onboarding-durable-email-v3` and preserve origin checks, closed schemas, response caps, timeouts, headers, and direct-node fail-closed behavior.
3. Deploy that exact reviewed commit to Preview only.
4. Read back the deployment ID, commit SHA, Preview alias, served assets, and proxy target.
5. Verify Production SHA, deployment, canonical DNS, and predecessor workflow ownership remain unchanged.
6. Verify desktop/mobile copy says `Check your email to continue onboarding` and success requires `email:"queued"`.

### Gate 7 — optional canary

A canary requires new explicit authorization because the prior authorization was consumed.

If authorized, use exactly one synthetic non-customer submission and reconcile all of these independently:

- one immutable submission claim;
- one exact Sheets row;
- one outbox row;
- one Gmail API request attempt;
- authoritative Gmail API acceptance or `ambiguous` state;
- no duplicate request after timeout or browser replay;
- no claim of inbox delivery.

## Rollback order

1. **Route first:** restore Preview application routing to `/webhook/pkc-onboarding-consent-v1` and read back the served proxy target.
2. Verify the predecessor path has exactly one active owner and Preview behavior is restored.
3. Stop new v3 intake by deactivating it only after separate approval and exact readback.
4. Do not down-migrate migration `003`; its rows are delivery/reconciliation evidence.
5. Do not delete, rewrite, or reset outbox rows.
6. Classify retained rows before changing worker state:
   - `blocked`: no Gmail request is authorized; retain.
   - `pending`: no Gmail request has been armed; either allow the reviewed worker to process it or pause before claim according to the incident decision.
   - `transmitting`: never resend; leave evidence intact and allow lease expiry to move it to `ambiguous`.
   - `ambiguous`: reconciliation-only; never return to `pending`.
   - `accepted`: terminal Gmail API acceptance evidence; never redispatch and never call it inbox delivery.
7. If the incident concerns the sender or HTTP serialization, deactivate the dispatcher after routing rollback and preserve all rows. Keep or separately pause the reconciler according to the incident boundary.
8. Deactivate the reconciler only with separate approval after all ambiguous rows have an explicit owner and follow-up plan.

## Failure and reconciliation rules

- A lost or malformed Gmail response after arming always becomes `ambiguous`.
- A Gmail search with zero results, multiple results, any `nextPageToken`, missing ID, malformed response, timeout, or unavailable provider is deferred; it never authorizes resend.
- A reconciliation acceptance requires exactly one Sent-mail result matching the database-generated RFC Message-ID.
- Manual replacement must create a new explicit delivery identity under a separately reviewed procedure; it must not reuse or erase the primary row.
- Public HTTP responses contain no email address, name, provider body, SQL detail, credential detail, stack, or reconciliation state.

## Completion evidence

A rollout gate is complete only after exact-target readback. A successful command or API response alone is not completion evidence. Any byte change after review invalidates prior hashes, tests, and reviewer verdicts.
